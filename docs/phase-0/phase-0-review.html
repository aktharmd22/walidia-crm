Blocking · Q5

Which lines are zero-rated or out of scope — charters outside UAE waters, security deposits, crew tips? Built as data, but the tax advisor signs off before Phase 3 ships.

02

Five decisions that shape everything else

Recorded with reasoning in DECISIONS.md. Each one is load-bearing: reversing it later is a rewrite, not an edit.

D-005

Pipeline stage is separate from lifecycle status

A booking's status is a fact about the booking; a deal's stage is a position on a board. One deals table drives all three pipelines, so the board, the gate checks and pipeline reporting are written once instead of three times.

D-004

The gate engine is data, not conditionals

Seventeen rules in gate_rules, one evaluator, a registry of small check classes, and every evaluation persisted — pass or fail. That is what makes “why was this charter allowed to sail” answerable a year later.

D-003

One yacht record, three capability profiles

The same 40-metre hull is chartered, listed and managed at once. Three subtype tables would guarantee three versions of its specs, photos and availability.

D-002 · D-011

The cost sheet is one object with three phases

Quoted, invoiced, actual — the client's own Cost & Offer table already flows that way, so P&L becomes a variance view for free. Money is computed in integer fils, never floats.

D-017

Visibility is a global scope, not controller filtering

A Sales user guessing another agent's client ID gets a 404 from every path — index, relation, search, report. Permissions and policies sit on top of that, never instead of it.

D-018 · D-019

Every entity gets complete CRUD

Index, create, store, show, edit, update, archive and restore for all 60+ business entities, plus nested CRUD on line items, bulk actions, and preview-then-commit import. Only system ledgers — audits, overrides, sequences — are read-only by design.

The gate engine

Eleven hard gates block the transition and can be overridden only by Admin, with a mandatory reason that lands in the Override Register permanently. 04

Where I would change the brief

Five places where following the brief literally would produce a worse system. Each has a proposal; none of them is a refusal to build what was asked.

  • Dietary and allergy data behind a VIP permission is an operational hazard. A charter cannot be catered by staff who cannot read the allergy list. Proposal: a time-boxed, logged grant to the Operations manager assigned to that booking, rather than a blanket permission — but this is a safety matter and should be decided explicitly.
  • The Phase 7 workflow builder is a product in itself. A general visual trigger-condition-action editor is weeks of work the team may configure twice. Ship the reminder engine, the gate rule editor and a catalogue of about fifteen configurable automations first; build the general builder only if the catalogue proves too rigid in real use.
  • PHPStan level 6 is the right floor, not the ceiling. Level 6 across the app, level 9 in the finance and gate namespaces — the two places where a type error is a money error or a safety error.
  • Full offline on Charter Day is not what “poor signal” needs. A durable retry queue with a visible pending-changes count solves the dock case at a fraction of the cost of real offline sync with conflict resolution. If genuine offline is required, it is a scoped addition with its own estimate.
  • Website sync should be one-way and status-only. CRM to WordPress over a signed endpoint: specs, public media, and availability as a state — available, on hold, booked. Never guest or client data, and never a write path back into the CRM.
